# Phase 0 Research — PosteType Catalog

**Feature**: 001-poste-type-catalog
**Date**: 2026-05-11

This document resolves the implementation unknowns surfaced during `/speckit-specify` and `/speckit-clarify`. Every entry follows the **Decision / Rationale / Alternatives considered** format. Items already resolved during `/speckit-clarify` are restated here as ratified decisions with full rationale.

---

## R-001 — Schema migration mechanism

**Decision**: Adopt **Flyway** (`flyway-core` + `flyway-database-postgresql`) as the sole schema-migration mechanism. Flip `spring.jpa.hibernate.ddl-auto` from `update` to `validate`. Migrations live in `src/main/resources/db/migration/` and follow `V<major>.<minor>__<description>.sql` naming.

Initial migrations:
- `V1.0__baseline.sql` — captures the **current** Hibernate-produced schema (validations, secteurs, phases, users, conversations, notifications, handovers, etc.) so existing prod and dev databases can be brought under Flyway control via `flyway.baseline-on-migrate=true` + `flyway.baseline-version=1.0`. Generated by running `pg_dump --schema-only` on a clean dev DB and hand-edited to remove Postgres-specific artifacts that Flyway will re-apply.
- `V1.1__poste_catalog.sql` — DDL for the new `poste_measure_catalog` table.
- `V1.2__seed_poste_catalog.sql` — Idempotent `INSERT ... ON CONFLICT DO NOTHING` of reference rows for `TEST_FONCTIONNEL`, `WIFI_CONDUIT`, `ACC`.

**Rationale**:
- Plan.md already named SQL files in the Flyway `V*` convention.
- SQL-first migrations are reviewable in PR diffs.
- `ddl-auto=validate` provides safety net (startup fails if entity ↔ schema drift).
- Constitution §Additional Constraints mandates Liquibase **or** Flyway; either is compliant, Flyway is lighter weight.

**Alternatives considered**:
- **Liquibase** — verbose XML/YAML changelogs; rollback support is nice but unused in our context. Rejected for ergonomics.
- **Keep `ddl-auto=update` + ApplicationRunner seed** — no schema governance, silent drift, no rollback story, can't ship V1.2 reliably. Rejected.

## R-002 — Bringing the existing schema under Flyway control (baseline)

**Decision**: On the first deployment of this phase, the Flyway `baseline-on-migrate=true` + `baseline-version=1.0` flags are set in `application.properties`. Flyway will treat the existing schema as "version 1.0" without applying `V1.0__baseline.sql` to environments that already have those tables. Fresh databases (CI, dev resets, Testcontainers) apply `V1.0__baseline.sql` from scratch.

Properties added:
```
spring.flyway.enabled=true
spring.flyway.baseline-on-migrate=true
spring.flyway.baseline-version=1.0
spring.flyway.locations=classpath:db/migration
```

**Rationale**: Existing dev/prod databases were created by `ddl-auto=update`; their schema must not be wiped. Baseline-on-migrate is the canonical Flyway adoption recipe.

**Alternatives considered**: Drop and recreate the dev DB (acceptable for the developer's laptop, unacceptable as a project-wide rule).

## R-003 — Uniqueness of `(posteType, measureCode)` for soft-deleted templates

**Decision**: Enforce uniqueness via a **partial unique index** that applies only to active rows:

```sql
CREATE UNIQUE INDEX uk_poste_measure_catalog_active
    ON poste_measure_catalog (poste_type, measure_code)
    WHERE active = true;
```

Inactive (`active = false`) rows are not constrained, so a curator may soft-delete a template and then create a new one with the same `(posteType, measureCode)` pair. Historical references to the old (inactive) template survive.

**Rationale**:
- Edge case "Soft-deleted template referenced by historical ticket measures" in spec.md.
- Edge case "Same measure code across different postes" naturally satisfied (uniqueness is on the pair).
- HTTP 409 in FR-004 is triggered only by an attempt to create a second **active** row with the same pair.

**Alternatives considered**:
- Full unique constraint on `(poste_type, measure_code)`: would forbid the soft-delete-then-recreate pattern. Rejected.
- Unique constraint on `(poste_type, measure_code, active)`: would forbid a second inactive row with the same code, harming history-keeping. Rejected.

## R-004 — Spring Data JPA auditing (audit quartet from clarification Q4)

**Decision**: Enable JPA auditing globally on `SagelineApplication` via `@EnableJpaAuditing(auditorAwareRef = "auditorProvider")`. Provide a `Config/JpaAuditingConfig.java` exposing:

```java
@Bean
public AuditorAware<Long> auditorProvider(SecurityUtils securityUtils) {
    return () -> {
        try { return Optional.ofNullable(securityUtils.getCurrentUserId()); }
        catch (Exception e) { return Optional.empty(); }
    };
}
```

`PosteMeasureCatalog` declares `@EntityListeners(AuditingEntityListener.class)` and the four fields:
- `@CreatedDate Instant createdAt`
- `@LastModifiedDate Instant updatedAt`
- `@CreatedBy Long createdBy`
- `@LastModifiedBy Long updatedBy`

Audit columns are populated for **all** mutations including the soft-delete (which is just an update flipping `active`).

**Rationale**:
- `SecurityUtils.getCurrentUserId()` already exists and resolves the DB user from the JWT `sub` claim.
- Spring Data JPA auditing is built-in; no extra dependency.
- `Optional.empty()` on no-auth allows the Flyway seed migration to leave the columns NULL (system-seeded rows). DDL allows NULL on the actor columns.

**Alternatives considered**:
- Hibernate Envers full audit history — overkill; we only need who/when, not historical row versions. Rejected for this phase (could be added in Phase 005 if compliance audit demands it).
- Manual setters in the service layer — error-prone, easy to forget on new endpoints. Rejected.

## R-005 — Mutability of `mandatory` and snapshot semantics (from clarification Q2)

**Decision (for this phase)**: The `mandatory` column on `poste_measure_catalog` remains **mutable** (update endpoint allows changing it). The catalog response DTO surfaces the current `mandatory` value explicitly so Phase 002's ticket-creation flow can copy it onto the per-ticket `ValidationMeasure` row. This phase does not implement the snapshot itself — only the obligation that the API exposes the value.

A note is added to the response DTO Javadoc and to the OpenAPI description: *"Snapshot this value onto the ValidationMeasure at ticket-creation time; do not re-read on transition."*

**Rationale**: Honors the audit posture decided in Q2 without dragging Phase 002 design into this phase. Backwards-compatible if Phase 002 chooses to model the snapshot as a `mandatoryAtCreation` column on `ValidationMeasure`.

**Alternatives considered**:
- Make `mandatory` immutable on the catalog and require soft-delete + recreate to change it. Rejected — catalog curation in Q2 explicitly preserved mutability.

## R-006 — Atomic batch creation

**Decision**: The batch endpoint accepts a payload of `{ posteType, items: [PosteMeasureCatalogRequest, ...] }`. The service method is `@Transactional`. Validation pipeline:

1. Per-item DTO validation (Jakarta Bean Validation, runs at controller boundary).
2. In-batch duplicate detection: scan `items[].measureCode` for duplicates → if any, throw `BatchValidationException` mapped to HTTP 422 with a per-index error list.
3. Bulk uniqueness check: `SELECT measure_code FROM poste_measure_catalog WHERE poste_type = :pt AND active = true AND measure_code IN (:codes)` → if non-empty result, throw `DuplicateCatalogTemplateException` mapped to HTTP 409 with the conflicting codes.
4. Inverted-bounds check on each item (`lower >= upper`) → HTTP 422.
5. `repository.saveAll(entities)`.

If any step throws, the `@Transactional` rollback ensures zero rows persisted.

**Rationale**: Spring's default declarative transactions provide atomic rollback on any unchecked exception. The pre-check `SELECT` + `saveAll` pattern keeps the conflict response specific (we name the offending codes) while staying within a single transaction.

**Alternatives considered**:
- Per-item `try/catch` with partial success — violates the "all or nothing" requirement (FR-013). Rejected.
- Application-level lock on `posteType` — overkill at this scale. Rejected.

## R-007 — Idempotent seed (FR-015)

**Decision**: `V1.2__seed_poste_catalog.sql` uses `INSERT ... ON CONFLICT (poste_type, measure_code) WHERE active = true DO NOTHING` for each row. Combined with Flyway's own checksum mechanism (a migration is applied once per database), the seed is doubly idempotent:

- Flyway's `schema_history` ensures the file runs once per fresh DB.
- The `ON CONFLICT DO NOTHING` clause guards against manual re-runs or partial-state recovery scenarios.

**Rationale**: Flyway's once-per-DB guarantee is sufficient in normal operation; `ON CONFLICT` is the belt-and-braces guard for ops scenarios (manual seed top-up after a curator deletes a critical template).

**Alternatives considered**:
- Java-side seed via `ApplicationRunner` (rejected — couples seed to startup, race conditions with Flyway, harder to version).

## R-008 — Role mapping to `@PreAuthorize`

**Decision**:

| Endpoint | `@PreAuthorize` |
|----------|------------------|
| `GET /api/poste-catalog` | `isAuthenticated()` |
| `GET /api/poste-catalog/postes` | `isAuthenticated()` |
| `GET /api/poste-catalog/{posteType}` | `isAuthenticated()` |
| `GET /api/poste-catalog/{posteType}/measures` | `isAuthenticated()` |
| `GET /api/poste-catalog/measures/{id}` | `isAuthenticated()` |
| `POST /api/poste-catalog/measures` | `hasAnyRole('ADMIN_IT', 'CHEF_SECTEUR')` |
| `POST /api/poste-catalog/measures/batch` | `hasAnyRole('ADMIN_IT', 'CHEF_SECTEUR')` |
| `PUT /api/poste-catalog/measures/{id}` | `hasAnyRole('ADMIN_IT', 'CHEF_SECTEUR')` |
| `DELETE /api/poste-catalog/measures/{id}` | `hasAnyRole('ADMIN_IT', 'CHEF_SECTEUR')` |

Role names match the existing `Role` enum (`ADMIN_IT`, `CHEF_SECTEUR`, `EXPERT`, `TECH_PREP`, `TECH_VAL`, `RESPONSABLE`); the `KeycloakJwtConverter` already prefixes with `ROLE_`.

**Rationale**: Plan.md §6 specifies write access for `ADMIN_IT` and `CHEF_SECTEUR`; read is open to all authenticated users per FR-016. Method-level `@PreAuthorize` matches existing controllers (e.g., `HandoverController`).

**Alternatives considered**:
- URL-level rules in `SecurityConfig` — already used as a secondary layer; method-level is canonical per the project's CLAUDE.md. Kept as method-level.

## R-009 — Seed sourcing and `active=false` contingency (from clarification Q3)

**Decision**: `V1.2__seed_poste_catalog.sql` is hand-authored from the three supervisor log files. The final-summary block of each log (regex documented in Plan.md §9) provides `(measureCode, label, status, min, max, measured, unit)` for every measure. Mapping:

| Log file | PosteType | Expected row count |
|----------|-----------|--------------------|
| `bnft-decoder-M393.txt` | `TEST_FONCTIONNEL` | ≥ 6 (PWR0_2G, PWR1_2G, PWR0_5G, PWR1_5G, PWR0_BT, Temps_Test) |
| `bwc-gateway-safran-wifi5g.log` | `WIFI_CONDUIT` | ≥ 16 (POWER_RMS_AVG_VSA1 × 4 antennas × 4 frequencies; plus PER, RSSI) |
| `btf-gateway-fb107-wifi7.log` | `ACC` | ≥ 14 (FXS current/voltage/ring/300/1000/3400 Hz transmission, consumption, sensors) |

Any row whose log entry lacks explicit `[min, max]` bounds is inserted with `active = false` and an inline SQL comment of the form:
```
-- SOURCE: btf-gateway-fb107-wifi7.log; observed=12.3 mA; bounds=placeholder (±5%); needs engineering review.
```

A curator (`ADMIN_IT` / `CHEF_SECTEUR`) calls `PUT /api/poste-catalog/measures/{id}` with engineering-validated bounds + `active=true` before that template participates in any ticket.

**Rationale**: Q3 decision; protects Phase 005 conformity engine and Phase 006 KPIs from being driven by synthetic bounds (Constitution Principle I).

**Alternatives considered**:
- Seed with `mandatory=false, active=true, bounds=measured±5%` (rejected as Option A in Q3 — synthetic bounds enter conformity).
- Omit those rows entirely (rejected — log importer in Phase 004 needs the measure code to exist).

## R-010 — Testing strategy

**Decision**: Three tiers, executed by `mvn test`:

1. **Repository tests** (`@DataJpaTest` + Testcontainers PostgreSQL) — verify the partial unique index, JPA auditing population, soft-delete behavior, and Flyway migration apply cleanly.
2. **Service unit tests** — mock the repository, assert validation logic (inverted bounds, in-batch dup detection, atomic batch rollback on simulated repo exception).
3. **Controller contract tests** (`@WebMvcTest` + `@MockBean` service) — assert HTTP status codes and DTO shape per role (using `SecurityMockMvcRequestPostProcessors.jwt().authorities(...)`). One test per FR-004, FR-005, FR-009, FR-010..013, FR-017, FR-018.
4. **Seed integration test** (`@SpringBootTest` + Testcontainers) — bootstrap an empty DB, let Flyway run, assert SC-001 (≥36 active templates across the three seeded postes) and SC-005 (restart the context, count unchanged).

Coverage target: 80 % line coverage on `service/` and `controller/` packages, measured by Jacoco.

**Rationale**: Mirrors existing test patterns in the SageLine codebase (`HandoverService` tests follow the same tiering). Testcontainers eliminates the "works on my dev DB but not in CI" failure mode that `ddl-auto=update` historically masked.

**Alternatives considered**:
- H2 in-memory DB for tests — rejected because the partial unique index (`WHERE active = true`) requires PostgreSQL semantics; H2's SQL dialect emulation is unreliable for partial indexes.

## R-011 — Logging & observability (Outstanding item from clarification)

**Decision**: Use SLF4J via Lombok `@Slf4j` on `PosteCatalogServiceImpl`. Log at INFO on every mutating operation:
- create: `"Created poste-catalog template {} for posteType={} by user={}"`
- update: `"Updated poste-catalog template id={} by user={} (fields changed: {})"`
- soft-delete: `"Deactivated poste-catalog template id={} by user={}"`
- batch: `"Batch-created {} poste-catalog templates for posteType={} by user={}"`

No metrics endpoint introduced in this phase. Observability beyond logs is deferred to a project-wide initiative.

**Rationale**: Matches existing logging style across the codebase. INFO level is appropriate for low-frequency curation events; DEBUG would hide them in production.

**Alternatives considered**:
- Micrometer `Counter` per mutation type — premature for this phase given low write volume. Deferred.

## R-012 — `measureCode` validation (Outstanding item from clarification)

**Decision**: `measureCode` is validated by `@Pattern(regexp = "^[A-Z][A-Z0-9_]{1,63}$")` on the request DTO. This admits every code observed in the three supervisor logs (`MES_BNFT_PWR0_2G`, `M_FXS_TRANS_FXS1_1000HZ`, `POWER_RMS_AVG_VSA1`) and bans lowercase, spaces, hyphens, and over-long identifiers.

**Rationale**: Plan.md examples all conform. Tightening at the DTO layer is cheap and stops typos before they hit the DB unique index.

**Alternatives considered**:
- No format check (rejected — typos like `power_rms_avg_vsa1` would silently create a duplicate-looking but distinct catalog entry).
- Whitelist enum (rejected — codes are open-ended; the catalog itself is the registry).
